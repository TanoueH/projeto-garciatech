# AGENTS.md — Construction Science Agents

## 1. Project Mission

This repository contains the MVP stack for **Construction Science Agents**, a multi-agent platform for construction management, operational documentation, daily reports, pending issues, document handling, scheduling support, and integration with construction company systems.

The system is not a simple n8n automation. It is an agent-based architecture where:

* **n8n is the message gateway / courier**
* **AI Agents are the reasoning layer / brain**
* **RPA is the execution layer / hands**
* **PostgreSQL is the operational memory and audit layer**
* **Dashboards are the observability layer**
* **Human users supervise and approve sensitive actions**

The project must prioritize auditability, traceability, operational safety, and incremental development.

---

## 2. Architecture Principles

### 2.1 n8n is not the brain

n8n must be treated as a message gateway, router, webhook handler, and notification layer.

n8n may:

* receive WhatsApp, e-mail, form, and webhook events;
* normalize simple transport metadata;
* route messages to the API Core;
* deliver responses and notifications;
* trigger controlled webhooks;
* export workflows for version control.

n8n must not:

* concentrate complex business logic;
* make final operational decisions;
* execute critical RPA actions directly;
* contain large amounts of JavaScript that should live in the API Core or agent layer;
* become the main source of truth.

### 2.2 AI Agents are the brain

AI Agents are responsible for interpretation, classification, reasoning, planning, extraction, summarization, and generation of structured commands.

Agents may:

* classify incoming messages;
* extract construction activities, materials, labor, equipment, issues, documents, and evidence;
* generate draft daily reports;
* generate pending issues;
* prepare quotation requests;
* prepare document registration commands;
* recommend actions;
* create auditable commands for RPA execution.

Agents must not:

* execute external system actions directly;
* bypass validation;
* bypass database logging;
* bypass human approval for sensitive actions;
* invent missing operational data when the input is ambiguous.

### 2.3 RPA never decides

RPA is exclusively an execution tool.

RPA must never interpret raw WhatsApp, e-mail, or user messages by itself.

Every RPA execution must come from a structured and auditable command generated by an AI Agent and recorded in the database.

Mandatory flow:

```text
Incoming message
    ↓
n8n / Message Gateway
    ↓
API Core
    ↓
AI Agent
    ↓
Auditable Command
    ↓
Policy / Validation / Human Approval when required
    ↓
RPA Executor
    ↓
External Construction System
    ↓
Execution Result + Evidence
    ↓
Database + Notification
```

RPA must record:

* command ID;
* origin agent;
* target system;
* payload received;
* execution status;
* execution timestamp;
* result;
* error message, if any;
* screenshots, files, logs, or other evidence when applicable.

## 3. Project Structure & Module Organization

The FastAPI service lives in `app/`, with `app/main.py` as the API entry point and `app/workers/agent_worker.py` for background agent execution.

Operational scripts are in `scripts/`, including OpenProject Excel utilities and SQL under `scripts/sql/`.

Infrastructure definitions for Docker, PostgreSQL, n8n, Grafana, MinIO, and related services are in:

```text
docker-compose.yml
docker-compose.override.yml
infra/
```

n8n workflow exports belong in:

```text
infra/n8n/workflows/
```

Documentation belongs in:

```text
docs/
docs/agents/
docs/workflows/
```

Local dashboard HTML files are in:

```text
dashboard/
```

Runtime data, imports, outputs, debug files, and generated reports are under:

```text
data/
outputs/
logs/
```

Avoid committing runtime artifacts unless they are intentionally used as fixtures, examples, or documentation assets.

## 5. Coding Style & Naming Conventions

Use Python 3 with:

* 4-space indentation;
* explicit names;
* small functions;
* type hints where they clarify API contracts;
* Pydantic models for request and response validation;
* clear error handling;
* structured logs where possible.

Use `snake_case` for:

* Python files;
* functions;
* variables;
* SQL tables;
* SQL columns;
* JSON field names controlled by this project.

Name n8n workflow exports with agent and version context, for example:

```text
agente_02_gerador_diario_obra_0_1_0.json
```

Prefer moving reusable logic out of n8n Code nodes and into the API Core or dedicated Python modules.

## 6. Database and Auditability Rules

PostgreSQL is the operational memory of the system.

Database changes must be explicit, reviewed, and traceable.

When adding or changing database behavior:

* prefer migrations under `infra/postgres/migrations/` or `scripts/sql/migrations/`;
* add validation queries under `scripts/sql/consultas/`;
* do not make destructive schema changes without backup and explanation;
* preserve idempotency for incoming messages and agent executions;
* use JSONB for structured operational payloads when appropriate;
* store source payloads when they are needed for auditability.

Critical actions must have a clear audit trail:

```text
who/what triggered the action
which agent interpreted it
which command was generated
whether approval was required
who approved it
which tool executed it
what result was produced
which evidence was saved
```

Recommended command status values:

```text
PENDENTE
AGUARDANDO_APROVACAO
APROVADO
REJEITADO
EM_EXECUCAO
CONCLUIDO
ERRO
CANCELADO
```

## 7. RPA Command Policy

RPA commands must be structured records, preferably stored in a dedicated table such as:

```text
comandos_rpa
```

Each command should contain at least:

```text
id_comando
obra_codigo
agente_origem
tipo_comando
sistema_destino
payload_comando
justificativa
status
requer_aprovacao
aprovado_por
aprovado_em
executado_por
executado_em
resultado
evidencias
mensagem_erro
criado_em
atualizado_em
```

The RPA layer may only execute commands with a valid status and valid payload.

Actions that normally require human approval include:

* saving an official daily report into an external system;
* changing schedule data;
* sending financial or quotation-related messages;
* closing critical pending issues;
* deleting or overwriting documents;
* modifying records in third-party systems.

Actions that may be automatic include:

* creating internal draft records;
* generating summaries;
* registering non-critical pending issues;
* notifying receipt of a message;
* saving files to a staging area;
* generating validation reports.

## 8. Testing Guidelines

No complete automated test suite is currently tracked.

For API changes, at minimum:

```bash
docker compose up -d
docker compose ps
curl -s http://127.0.0.1:8000/status/health | python3 -m json.tool
```

Also test at least one representative webhook request from the README or documentation.

For database changes:

* add or update SQL validation queries;
* verify inserts, updates, constraints, and JSONB fields;
* test idempotency behavior where relevant.

For n8n changes:

* export the workflow JSON;
* store it in `infra/n8n/workflows/`;
* document the change in `docs/workflows/`;
* test both success and error paths;
* verify that the workflow does not bypass the API Core for critical decisions.

For RPA changes:

* test only in sandbox first;
* never run against production systems without explicit approval;
* store evidence of the execution;
* verify that execution came from an approved command.

If adding Python tests, place them in:

```text
tests/
```

Use:

```text
test_*.py
```

and prefer `pytest` conventions.

## 10. Security & Configuration Rules

Never commit:

* `.env`;
* credentials;
* API keys;
* tokens;
* passwords;
* raw exports containing secrets;
* debug payloads with private data;
* database dumps with sensitive information;
* private phone numbers;
* production webhook URLs with secrets.

Before committing, scan staged changes for common secret patterns:

```bash
git diff --cached | grep -niE "sk-|apikey|api_key|password|passwd|pwd|secret|token|credential|authorization|bearer|access_key|secret_key"
```

Prefer using a dedicated secret scanner such as:

```bash
detect-secrets
gitleaks
```

Files containing local passwords or operational credentials must be removed from version control and replaced by `.env.example` templates.

---

## 11. Prohibited Actions Without Explicit Approval

Do not run destructive or high-impact commands without explicit user approval and explanation.

Examples:

```bash
docker compose down -v
rm -rf
DROP TABLE
DROP DATABASE
TRUNCATE
DELETE FROM
git reset --hard
git clean -fd
```

Do not edit `.env` files directly unless explicitly instructed.

Do not overwrite n8n workflow exports without creating a backup or confirming versioning.

Do not modify production-like data when a sandbox or staging path is available.

---

## 12. Agent Behavior Rules

Before editing files, the agent should:

1. inspect the relevant files;
2. explain the diagnosis;
3. propose a small plan;
4. apply minimal changes;
5. show a summary or diff;
6. provide validation commands.

The agent should prefer incremental, reversible changes.

The agent should not introduce new services, dependencies, or architectural layers unless the benefit is clear and documented.

When in doubt, preserve the architecture:

```text
n8n = message gateway
API Core = controlled entry point
AI Agents = reasoning layer
PostgreSQL = operational memory
RPA = audited execution layer
Dashboards = observability
Human = supervisor for sensitive actions
```
